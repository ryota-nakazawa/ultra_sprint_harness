# findings.md — 問い合わせ一次対応トリアージ ドライラン

## 結論

この入力例は Web App ルートに自然に流れ、追加した計測テンプレートも discovery から内側ループ判定まで機能した。
15 分デモ用の成果物としては、分類精度そのものより「分類結果を見て、修正して、投資判断の論点を出す」体験を見せるのが最小。

## 今回作ったもの

- `interview-summary.md`: ユーザー提供内容を案件入力として保存
- `project-requirements.md`: discovery と routing の結果を整理
- `acceptance-criteria.md`: 第1層 4 項目、第2層 7 項目を Yes / No 条件で記録
- `sprint-metrics.md`: 内側ループの結果を記録
- `index.html` / `styles.css` / `app.js`: 静的な Web App プロトタイプ

## 検証結果

| 観点 | 結果 |
|---|---|
| 初期表示 | 40 件のモック問い合わせを表示 |
| 自動分類 | 緊急度（高・中・低）とカテゴリを付与 |
| ダッシュボード | 全件、緊急度高、要確認、修正済み、カテゴリ別件数を表示 |
| 修正操作 | 選択行の緊急度・カテゴリを修正し、集計に反映 |
| CSV 取り込み | ヘッダー付き CSV を読み込み、一覧を差し替え |
| ブラウザエラー | なし |

## 残した仮説

- CS 部長が見たいのは、AI が完全自動で正解することではなく、現場が信頼できる補助線になるかどうか。
- 経営企画が見たいのは、投資判断に向けて次に何を測るべきかが見えること。
- 次の実顧客デモでは、現場担当者が 10 件だけ手修正し、どの分類観点がズレるかを記録するとよい。

## 次に検証すること

- 緊急度「高」の見逃しをどこまで許容できるか
- カテゴリ分類の誤りを現場が何秒程度で修正できるか
- 本格導入時に、メール・Web フォーム・既存 CS システムのどこからデータを受けるか
