# acceptance-criteria.md — PoC 成立条件と Eval Spec

> **書くタイミング**: discovery（要件整理）の最後。**実装を始める前に確定させる。**
> 成果物ができた後に条件を足したり緩めたりしない。変更が必要になったら末尾の「変更履歴」に理由つきで残す。
> **記入の目安**: 10〜15分。
>
> **条件文のルール**: すべて「Yes / No で答えられる文」で書く。
> - ❌ 使いやすい画面 → ⭕ CSV をアップロードすると 3 秒以内に一覧が表示される
> - ❌ エラーに強い → ⭕ 不正な入力をしたとき、日本語のエラーメッセージが表示される
>
> Yes / No の文に書き換えられない条件は、まだ曖昧さが残っているサイン。discovery に戻って具体化してから実装に進む（この変換の完了を discovery の完了条件とする）。
>
> **評価観点**: 第2層の条件は `業務成功 / 誤実行 / 安全性 / 再現性 / 運用負荷` のどれを主に見るか分類する。
> **評価の独立性**: LLM で判定する場合は、実装を担当したエージェントではなく、別コンテキストの評価エージェントに渡す。
> 評価エージェントには成果物、実行手順、`project-requirements.md`、このファイル、`eval-cases.md`、`eval-profile.md`、必要時の `traceability.md` だけを渡し、実装中の会話ログや言い訳は渡さない。

## 6. デモ後のふりかえり（第3層の結果を受けて）

第3層（顧客デモ）の結果が出たら 1 行だけ書く。**条件を全部満たしたのに意思決定につながらなかった場合、それはこのファイルの条件（＝仮説）のズレ**なので、どの条件が顧客の関心とズレていたかを findings.md に残し、次案件の条件づくりの教材にする。
デモや利用中に見つかった失敗は、再現できる形で eval-cases.md の「追加ケース候補」に戻す。
