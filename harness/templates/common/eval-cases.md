# eval-cases.md — 軽量 Evals ケース集

> **書くタイミング**: discovery の最後に初期版を作り、動作確認・デモ・レビューで見つかった失敗を随時追加する。
> **目的**: 感覚的な評価を、次回も再現できるケースに変換する。
> **記入の目安**: 初回は 3〜7 件。代表ケース、境界ケース、失敗ケースを最低 1 件ずつ含める。
>
> 自動 grader や eval runner は v1 では前提にしない。人間または LLM が読んで判定できる粒度にする。
> LLM で判定する場合は、実装を担当したエージェントではなく、別コンテキストの評価エージェントを使う。
> 評価エージェントには成果物、実行手順、`project-requirements.md`、`acceptance-criteria.md`、このファイル、`eval-profile.md`、必須の `traceability.md` だけを渡し、実装中の会話ログや背景説明は渡さない。
> 自動ループは最大 2 回まで。3 回目の実装・評価には入らない。明確に直せる不合格だけ `Fix` とし、判断が必要なものは `Needs Review` として止める。

> **評価起動の証跡**: 評価エージェントを起動したオーケストレーターは、各評価ごとに `evaluation/runs/{run-id}/` を作る。`receipt.json` には起動時に返された agent ID、`fresh_context`、許可した入力に加え、評価時点の commit / 入力 / 成果物 hash とモデル設定を記録し、`evaluator-input.md` と `evaluator-result.md` を保存する。

## 1. 評価観点

該当する観点だけ使う。迷う場合は `業務成功` を基本にし、危ない失敗だけ `誤実行` または `安全性` に分ける。

| 観点 | 見ること |
|---|---|
| 業務成功 | ユーザーがやりたい仕事を最後まで進められるか |
| 誤実行 | 不要な操作、誤った分類、誤ったツール実行をしていないか |
| 安全性 | 確認が必要な場面で止まれるか、権限外の操作をしないか |
| 再現性 | 同じ条件で同程度の結果になるか |
| 運用負荷 | 遅すぎる、直しにくい、レビュー負担が大きすぎる状態になっていないか |

## 2.5 評価エージェントへの入力

LLM 判定を使う場合は、評価エージェントに次だけを渡す。

- 成果物
- 成果物の実行手順
- `acceptance-criteria.md`
- `eval-cases.md`

渡さないもの:

- 実装中の会話ログ
- 実装者の判断理由や言い訳
- 途中で迷った案
- 未完成箇所の補足説明

評価エージェントは、各項目について `ID / 評価観点 / Pass / Fix / Needs Review / 根拠 / 不合格時の再現手順` を返す。
`acceptance-criteria.md` とこのファイルで宣言した評価観点だけを判定対象にし、定義していない品質を推測して減点しない。安全性、権限、送信、削除などの高影響操作に不明点があれば、`Fix` ではなく `Needs Review` とする。

## 2.6 自動評価ループの停止条件

評価結果は次の 3 つに分類する。

| 結果 | 意味 | 次の動き |
|---|---|---|
| Pass | 条件を満たしている | 完了 |
| Fix | 明確に直せる不合格 | 実装へ戻して修正し、再評価する |
| Needs Review | 人間判断が必要 | 要チェックとして記録し、自動ループを止める |

`Fix` にしてよいもの:

- 明らかな未実装
- 文言ミス
- 壊れた導線やエラー
- acceptance / eval-case に照らして明確に No のもの

`Needs Review` にするもの:

- 要件や評価基準が曖昧
- 顧客判断が必要
- スコープを広げないと直せない
- 主観的な良し悪し
- セキュリティ、権限、送信、削除などリスクが高い操作

自動ループは次のいずれかで止める。

- すべて `Pass` になった
- `Needs Review` が 1 件以上出た
- run全体の `Fix` が 2 回発生した（2 回目の Fix 後、3 回目の実装・評価には入らない）
- 修正にスコープ変更や評価基準変更が必要になった

## 2.7 評価実行の証跡

LLM 評価を実行した回数だけ、次の構成を作る。評価ログ本文だけでは、別コンテキストのサブエージェントが実際に起動した証明にならないためである。

```text
evaluation/runs/
  {UTC timestamp}-iteration-{NN}/
    receipt.json
    evaluator-input.md
    evaluator-result.md
```

1. オーケストレーターが `fresh_context` で評価サブエージェントを起動する。
2. 起動 API が返した agent ID を `receipt.json` に記録する。
3. 実際に渡した依頼文を `evaluator-input.md`、返答全文を `evaluator-result.md` に保存する。
4. `completed_at` と最終判定を `receipt.json` に追記する。

新規runは、次の補助コマンドで receipt の再現情報を先に作れる。`--artifact` は評価対象の成果物ファイルを 1 件以上指定する。

```bash
python3 tools/create_evaluation_run.py \
  --project-dir projects/{プロジェクト名} --iteration 1 --agent-id {agent-id} --scope non_ui \
  --model {model} --temperature 0 --prompt-version prompt-v1 --rubric-version rubric-v1 \
  --artifact path/to/artifact
```

正式な `Pass / Fix / Needs Review` をこのファイルへ記録する前に、`python3 tools/check_evaluation_evidence.py --project-dir projects/{プロジェクト名}` を実行する。評価後に成果物・要件・eval casesが変わるとhash検査が失敗し、その過去runは監査履歴として残るが現在の正式判定には使えない。失敗時は、結果を `未判定` のままにし、`evaluation-status.md` に自己確認だけを記録する。

ローカルの証跡は後から編集可能な運用ログであり、改ざん耐性は持たない。改ざん耐性が必要になった時だけ、CI 実行 ID や追記専用の外部ログへ移す。
