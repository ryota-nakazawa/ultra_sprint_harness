> **注意**: 件数（n）が 10 未満のルートは「率」として読まない。個別事例（findings）として読む。

## 1. ルート別集計

sprint-metrics.md から件数を数えて埋める。

| ルート | 件数 n | 一発合格率 S₁₂ | フォールバック率 | ルート切替率 | 第3層成功率 S₃ |
|---|---|---|---|---|---|
| Web App | | __ / n | __ / n | __ / n | __ /（デモ実施数） |
| Codex Skills | | | | | |
| GPTs | | | | | |
| Workflow・ハーネス設計 | | | | | |

- **S₁₂（一発合格率）**: 初回の成果物で第1・2層を全項目クリアした割合 →「作る力」の指標
- **S₃（第3層成功率）**: デモが意思決定に足る学びを生んだ割合 →「何を作るべきか判断する力」の指標
- **フォールバック率**: 結局人が主に作った割合 → 高いルートは「最初から人間がやる」候補（n ≥ 10 で判断）

## 2. 2×2 診断（失敗の切り分け）

当月の各スプリントを 4 象限に振り分けて件数を書く。

| | 第3層: 成功 | 第3層: 失敗 |
|---|---|---|
| **第1・2層: 一発合格** | __ 件（理想形） | __ 件（→ 要件＝仮説のズレ。discovery を改善） |
| **第1・2層: 手戻りあり** | __ 件（結果オーライだが非効率。→ ハーネス／成立条件の書き方を改善） | __ 件（→ 両方に課題。個別にふりかえり） |

**右上（作れたのに刺さらなかった）の案件は必ず 1 件ずつ確認する:**
どの成立条件が顧客の関心とズレていたか → 次案件の acceptance-criteria づくりに反映。

## 4. 検証 1 件あたりコスト（第3段階・任意）

金額の主張が必要になった段階で記入する。単価は社内の標準レート（人月単価等）でよい。

```
検証 1 件あたりコスト ＝（ G ÷ S₁₂ ＋ V ）÷ S₃

  G   : 1 スプリント試行の平均コスト（AI 費用 ＋ 人の作業時間 × 単価）
  S₁₂ : 一発合格率（上の表）
  V   : デモ 1 回あたりの準備・実施・整理コスト
  S₃  : 第3層成功率（上の表）
```
